# 分布データ生成フレームワーク アーキテクチャ

## 背景と想定課題

半導体製造の欠陥パターン解析では、**分布データ生成**の仕組みが不可欠です。実機データだけに頼ると、希少な欠陥パターンの検出や新たな原因仮説の検証が困難になります。またパターンの種類ごとに個別のスクリプトが乱立すると、コードの重複や不整合が生じ、再現性や比較可能性を損ないます。従来は各チームや分析者がばらばらに疑似データ生成ツールを作成していましたが、**開発者視点**では**21種類以上の欠陥パターン**に対応しようとすると条件分岐だらけのコードとなり（スパゲッティ化）、新しいパターン追加が非常に困難になる問題がありました。一方、**解析者視点**では生成データのパラメータ設定ミスにより**非現実的なデータ**を大量に作ってしまい、誤った分析結果を導くリスクも指摘されていました。

さらに、機械学習特有の課題として、粒子（欠陥点群）データの**ラベル管理の複雑化**があります。単純な実装では「パターン = 原因」とみなして単一のラベル体系で扱いがちですが、実際には**細分類ラベル（phenotype）**と**原因仮説ラベル**は別物です。既存手法ではラベル粒度が統一されておらず、分析者によってはパターン名をそのまま原因と誤認したり、ラベルが増えすぎて手に負えなくなるケースもありました。また一つのサンプル中に複数パターンが重畳する場合、従来は分析対象から外すか個別に処理していましたが、単一ラベルしか扱えないモデルでは**多重欠陥の再現**ができず、現実とかけ離れるという課題もありました。

以上の背景から、本プロジェクトでは**統一的な分布データ生成フレームワーク**を開発し、(1) 多彩な欠陥パターンの生成を一つのプラットフォームで実現し、(2) **Hydra**による一元的な設定管理で再現性・比較可能性を担保し、(3) **ラベルの多層管理**や**複合パターン生成**など機械学習向けの高度な機能を提供することを目指しました。これにより、都度自前開発していたコードの乱立を防ぎ、追加開発のハードルを下げるとともに、粒子データ解析における再現性・汎用性の課題を解決します。

## 想定ユーザー

本フレームワークの主な利用者は以下の二者です。

- **非データサイエンス系エンジニア（解析ユーザー）**：製造プロセスや装置エンジニアなど、データサイエンティストではないが欠陥パターンの分析やレポート作成を行うユーザーです。これらのユーザーは、コードの内部実装には立ち入らずに、設定ファイルやコマンドラインから必要な疑似データを生成し、統計解析や可視化結果を得たいと考えています。彼らにとって重要なのは、**専門知識がなくても多様なパターンのデータを簡単に生成できること**、および**生成物の信頼性（現実性・再現性）が保証されていること**です。

- **コード開発エンジニア（アーキテクト/データサイエンティスト）**：本コードの拡張や保守を担当する技術者です。新たな欠陥パターンや評価指標を実装したり、他ドメインへの展開（例：画像や時系列データへの拡張）を行う役割です。これらのユーザーにとっては、**アーキテクチャが拡張しやすく整理されていること**、すなわち追加実装の際に既存コードへ最小限の変更で済み、他機能への副作用が少ない設計であることが最重要です。また**実験の再現性**や**結果の検証容易性**（例えば乱数種の管理や出力物に十分なメタデータが含まれること）も欠かせません。

以下では、これら想定ユーザーごとに必要とされる機能や本コードで講じた対応策、その効果について整理します。

## 本コードの構成

本フレームワークのディレクトリ構成と各コンポーネントの役割を以下に示します。全体として**ドメイン固有の実装**と**共通フレームワーク**を明確に分離し、新たなドメイン追加やプラグイン拡張が容易な構造になっています。

```plaintext
synthlab_scaffold/
├── conf/                       # Hydra設定ファイル（YAML）の定義
├── src/                       
│   └── synthlab/
│        ├── cli/              # CLIエントリポイント（Hydra互換の設定合成）
│        ├── framework/        # フレームワーク共通機能（プロセス管理・Artifact管理・レジストリ等）
│        └── domains/
│             └── wafer_particles/   # ドメイン（ウエハ粒子欠陥）の実装
│                  ├── schema.py         # データスキーマ定義
│                  ├── generators/       # パターン生成器・粒径モデルの実装
│                  ├── metrics/          # QCメトリクス算出処理
│                  └── viz/              # 可視化処理
├── tests/                     # テストコード一式
└── runs/                      # 実行結果の出力ディレクトリ（Git管理外）
````

各フォルダ/モジュールの詳細と、役割・拡張時のポイントを以下の表にまとめます。

| 場所                           | 役割・内容                                                                                                                                                                                                                                                         | 開発時の留意点・拡張ポイント                                                                                                                                                                                                                                                                                                                                   |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **conf/**                    | Hydra用の設定YAML集。デフォルト設定は`conf/config.yaml`で定義し、`defaults`リストで**domain**（例: wafer_particles）や**process**（実行プロセス）を指定します。ドメインごとのサブフォルダに細かな設定ファイル群（パターン毎のYAML、サイズモデルYAML、QC閾値、出力形式設定など）が配置されています。                                                                  | 新しいドメイン追加時は`conf/domain/<domain_name>.yaml`を作成し、defaultsに組み込む必要があります。パターン追加時は該当ドメイン配下の`patterns/`にYAMLを1つ追加します。既存キーの意味を変える変更は**禁止**（blocked運用）なので、新規キー追加で対応してください。                                                                                                                                                                               |
| **src/synthlab/cli/**        | コマンドライン起動用のモジュール。Hydra互換のdefaults解決とCLI overrideで設定を合成し、指定された`process`に応じて実行を開始します。`conf/config.yaml`を基準に、必要なら`--config-path/--config-name`でベンチマーク用設定を重ねられます。                                                                                                                 | エントリポイントは`cli/main.py`で、`python -m synthlab.cli.main process=<name>`で起動します。ベンチマーク設定を使う場合は`python -m synthlab.cli.main --config-path conf/benchmarks/wafer_particles --config-name benchmark_macro5_300mm_1k_generate seed=42`のように指定します。通常、この部分は汎用的に実装してあるため**改変不要**です。他のプロセスを追加する際もframework側でdispatch対応すればCLIは変更せず利用できます。 |
| **src/synthlab/framework/**  | フレームワークの中核となる層。共通基盤として**プロセスディスパッチャ**（`process.py`）、**Artifact I/O管理**（`artifacts.py`）、**プラグイン登録機構**（`registry.py`）等を提供します。各Processの基本クラスや、ドメイン実装を呼び出す流れを定義しています。                                                                                             | **依存関係ルール**: framework層は下位（domains層）への依存を持ちません。この層を修正する際は他への影響範囲が大きいため注意が必要です。新しい種類のProcessを追加する場合、`process.py`にエントリを追加し、適切にドメイン側実装を呼ぶようにします。`registry.py`はパターンやメトリクスの登録先で、プラグインクラスにデコレータやエントリを追加することで自動登録されます。                                                                                                                                  |
| **src/synthlab/domains/**    | ドメイン固有の実装をまとめた層。現時点では`wafer_particles`（ウエハ上欠陥点群）のみ実装されていますが、将来的に画像ドメイン等を追加する想定です。各ドメインは**フレームワークと対称なインターフェース**を持ち、他ドメインと独立に拡張可能です。                                                                                                                            | 新ドメイン追加時には、この`domains/`配下に`<domain_name>/`ディレクトリを新設し、既存ドメインにならったサブ構成（schema.py, generators/, metrics/, viz/）を準備します。framework側コードには新ドメイン固有の分岐をできるだけ増やさず、プラグイン機構で対応することが望ましいです。                                                                                                                                                                    |
| **domains/wafer_particles/** | ウエハ粒子欠陥ドメインの具体実装。**スキーマ定義**（`schema.py`）では粒子データ（座標r,θやサイズなど）およびサンプルデータ（IDや各種集計）のカラム構造を定義します。**生成器**（`generators/`）では各欠陥パターンの生成クラス（Patternクラス群）や粒径サイズモデルを実装。また**QC指標**（`metrics/`）には例えば欠陥の広がりや密度分布統計の算出処理、**可視化**（`viz/`）には粒子配置の散布図プロットやサイズ分布ヒストグラム生成処理が含まれます。 | **パターン追加**: `generators/patterns/`フォルダに新しいPattern派生クラスを追加し、クラス内で`Pattern.generate()`などのインターフェースを実装します。同時に`conf/wafer_particles/patterns/<新パターン>.yaml`を用意し、必要なら`registry.py`に登録します（多くの場合デコレータ登録で自動認識されます）。**メトリクス追加**: `metrics/`に関数やクラスを追加し、QCプロセスから呼ばれるように設定します。**注意**: ドメイン層から直接HydraやCLIに依存せず、frameworkから渡された設定データ（コンフィグ辞書やRNG）を使うよう実装してください。 |
| **tests/**                   | 各種ユニットテスト・統合テストを格納。パターン生成のスモークテスト、乱数シードによる再現性テスト、設定検証エラー発生テスト、ラベル適用結果テストなど、多面的なテストがあります。                                                                                                                                                                      | 新規機能を開発した際は必ず対応するテストを追加します。特に再現性や不変条件に関わる部分はテストで保証してください（例：ランダム生成でもシードが同じなら同一結果になることをアサートするテスト）。テストコードは仕様の一部なので、docsや設計と乖離しないように保守しましょう。                                                                                                                                                                                                         |
| **runs/**                    | 実行結果の格納ディレクトリです。各実行時にHydraが自動生成し、`runs/<日時>/<プロセス名>/`以下に出力が保存されます（設定でカスタム可能）。典型的には`resolved.yaml`（解決済みコンフィグ）、`overrides.txt`（上書きパラメータ）、生成された`particles.parquet`や`samples.parquet`データ、`meta/`メタ情報、`reports/`統計レポート類が含まれます。                                     | **注意**: `runs/`以下はGit管理しません。大量データになる可能性があるため、不要になったら適宜クリーンアップしてください。runsディレクトリ構造はartifact契約に従い、直接手で編集・改変しないでください（生成物は基本immutable）。                                                                                                                                                                                                               |

このように、**ディレクトリごとに明確な責務分担**がなされています。アーキテクトは特にframework層と各ドメインの境界（インターフェース）が適切に保たれているか注意を払い、開発者は自分が変更すべき箇所（新規パターンならgenerators内と対応するYAML、など）に集中できる設計となっています。

## ユーザー向けマニュアル

ここでは、非データサイエンスエンジニアのユーザーを想定し、本コードの**利用手順**を説明します。環境構築からデータ生成・解析・出力までの流れを示し、必要に応じて入力/出力ファイルの形式や可視化例も交えて解説します。

### 環境構築

本フレームワークはPythonで実装されています。以下の手順で環境を整えてください。

1. **Pythonのセットアップ**: Python 3.9以上が必要です（開発時は3.10で動作確認）。仮想環境（venvやconda）を用意します。
2. **依存ライブラリのインストール**: リポジトリ内の`requirements.txt`を参照し、必要なパッケージをインストールします。主要ライブラリには**Hydra/OmegaConf**（設定管理）, **pandas**（データ処理）, **numpy**（数値計算）, **pyarrow**（Parquet入出力）, **matplotlib/seaborn**（可視化）などがあります。インストールコマンド例: `pip install -r requirements.txt`。
3. **リポジトリの取得**: Gitから本リポジトリをクローンするか、zipダウンロードして展開します。パスをPythonの`PYTHONPATH`に通すか、`pip install -e .`でeditableインストールしておくと、モジュールとして利用可能になります。
4. **初期設定**: `conf/`以下の設定ファイルはデフォルト値が入っています。まずはデフォルトのまま動作確認することをお勧めします。必要に応じ、`conf/wafer_particles/labeling/label_layers_example_v1.yaml`（ラベル層定義の例）を自分の用途に合わせて編集してください。

### 基本的な実行方法

本フレームワークはCLI（コマンドラインインターフェース）からHydra互換の設定合成で操作します。エントリーポイントは`src/synthlab/cli/main.py`で、`python -m synthlab.cli.main ...`の形式で実行します。必要に応じて`--config-path/--config-name`でベンチマーク設定を重ねられます。以下に主要な**プロセスごとの実行例**を示します（必要に応じて設定Overrideも併記）。

* **設定検証 (Doctor)**:

  ```bash
  $ python -m synthlab.cli.main process=doctor seed=1
  ```

* **データ生成 (Generate)**:

  ```bash
  $ python -m synthlab.cli.main process=generate wafer_particles.n_samples=1000 seed=42
  ```

* **ベンチマーク設定の利用 (Generate)**:

  ```bash
  $ python -m synthlab.cli.main \
      --config-path conf/benchmarks/wafer_particles \
      --config-name benchmark_macro5_300mm_1k_generate \
      seed=42
  ```

  - 例: ベンチマークYAMLの`defaults`では`wafer_particles/size_models: gaussian`のように**group: option**形式で指定します。
  - `wafer_particles.size_models`は`name/mean_um/std_um`など**モデル直下のキー**を持つため、`gaussian:`の入れ子は不要です。
  - `mean_um`/`std_um`などは`dist`指定で分布サンプリング可能で、`per_sample: true`ならサンプルごとに再サンプリングされます。
  - 粒子数のレンジ指定は`wafer_particles.n_particles_distribution`を使用します（`wafer_particles.patterns`配下に`defaults/param_space`は置かない）。
  - `profiles/`でパターンのパラメータ上書きを行う場合、該当パターンYAMLは**defaultsで必ず読み込む**（`patterns`の`name`が必要）こと。
  - macroベンチマークのラベルセットを変える場合は、`wafer_particles/labels: taxonomy_v2`のように**group defaultsで読み込む**とラベルメタが有効になります。
  - `label_coarse`/`label_family` はラベルメタが無い場合に `null` になり得るため、サンプル表では **optional列としてnull許容** です。

* **品質検証 (QC)**:

  ```bash
  $ python -m synthlab.cli.main process=qc input_dir="runs/.../generate"
  ```

* **可視化 (Viz)**:

  ```bash
  $ python -m synthlab.cli.main process=viz input_dir="runs/.../generate"
  ```

* **データセット書き出し (Export)**:

  ```bash
  $ python -m synthlab.cli.main process=export input_dir="runs/.../generate"
  ```

* **ラベル適用 (Labeling Apply)**:

  ```bash
  $ python -m synthlab.cli.main process=labeling_apply \
      input_dir="runs/.../export" \
      wafer_particles.labeling.spec_path="./conf/wafer_particles/labeling/label_layers_example_v1.yaml"
  ```

* **複合データ生成 (Compose)**:

  ```bash
  $ python -m synthlab.cli.main process=compose \
      input_dir="runs/.../generate" \
      compose.n_samples_out=100 compose.n_components=2 seed=123
  ```

* **パターン網羅性チェック (Pattern Coverage)**:

  ```bash
  $ python -m synthlab.cli.main process=pattern_coverage \
      input_dir="runs/.../compose"
  ```

### 入力ファイルと出力ファイル

* **入力ファイル**: 本フレームワーク独自の入力ファイルは基本的に**設定YAML**です。データ生成自体は内部で乱数生成するため外部データ入力は不要です。一部プロセス（labeling_applyやcompose、qc等）は`input_dir`として**既存のrunsディレクトリパス**を受け取ります。ユーザーが別途用意する可能性があるものとして、ラベル適用用の**ラベルスペックYAML**（外部ファイル）が挙げられます。

* **出力ファイル**: 出力は`runs/<日時>/<プロセス名>/`以下に自動生成される**artifact**群です。主なファイル・フォルダは以下の通りです。

  * `particles.parquet`： 全粒子（欠陥点）データテーブル。
  * `samples.parquet`： サンプル（ウエハ単位）データテーブル。
  * `meta/resolved.yaml`： 実行時に使用された**解決済み設定**。
  * `meta/overrides.txt`： 実行時にコマンドラインから指定したoverride一覧。
  * `reports/`： QCやCoverage、Labelingなどの解析結果レポート。
  * `plots/`： Vizプロセスで生成される画像（PNG）。

出力ファイルは基本的に**追記専用（immutable）**であり、同じrun内のファイルを後から編集・更新しない運用を想定しています。新たな解析や生成条件変更は新しいrunディレクトリを作って比較する設計です。

## 現在までの手段での課題

本フレームワークが解決を目指した課題について、従来手段との対比で整理します。

* **データ不足と属人化**: 生成・拡張が手作業に依存し、再現性が低い。
* **コードのスケーラビリティ不足**: パターン数増大でメンテ不能、追加開発が困難。
* **ラベル設計の欠如**: fineのみで説明性/原因推定が弱い。複合欠陥を扱えない。
* **再現性・比較困難**: 実験条件が揺らぎ、厳密比較ができない。
* **ドメイン展開困難**: 特定データ形式に特化し他ドメインへ転用しづらい。

## まとめ

本フレームワークは、欠陥点群（粒子）分布データ生成を **Hydra/Artifact/Process/Plugin** で統一し、以下を実現します。

* **拡張性**：パターン・指標・可視化をプラグイン化し、if/else地獄を回避
* **再現性**：seedとresolved configを保存し、比較可能性を担保
* **運用性**：doctor/QC/coverage/exportにより、生成→品質→配布の導線を整備
* **機械学習適合**：多層ラベル・複合欠陥（multi-label）にも対応

この設計により、少数実測しかない状況でも「生成→検証→学習→比較」を同一の契約で回せるデータ基盤として機能し、今後のドメイン拡張（画像/時系列）にも耐える骨格となっています。
